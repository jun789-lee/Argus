## 0. 한눈에 보기

- **만드는 것:** "AI가 일하고 → 검사받고 → 고치고 → 다시 검사받는" 반복을, **양식(스펙 파일) 하나만 채우면** 어떤 분야에서든 돌릴 수 있게 하는 기능. 실제 작업은 Claude Code가 하고, Argus는 설계·지휘·관찰을 맡는다.
- **가장 중요한 원칙:** 루프의 성패는 반복 횟수가 아니라 **검사(검증자)를 얼마나 믿을 수 있고, AI가 그 검사를 건드릴 수 없느냐**에 달려 있다(보고서 결론). 그래서 검사와 예산은 전부 **AI 손이 닿지 않는 바깥 프로그램(러너)**이 맡는다.
- **v1의 모양:** 반복 한 번 = 새 Claude Code 세션 한 번. 러너가 세션을 띄우고 → 끝나면 직접 채점하고 → 좋아졌으면 채택, 아니면 되돌리고 → 멈출지 정한다. Argus 화면에서 점수 추이, 각 반복의 세션 기록, 경고, 사람 확인 요청을 본다.
- **첫 적용:** 새로 참여할 Kaggle 대회 (대회는 미정, §15-1). 대회가 데이터형인지 시뮬레이션형인지에 따라 검증자 구성이 달라지므로 두 유형을 모두 §11에 정리했다. Kaggriculture(종료된 시뮬레이션 대회)는 시뮬레이션형의 구체 예시로 남겨 둔다.

## 1. 용어 (쉬운 말 정리)

| 용어 | 뜻 |
|---|---|
| **루프** | 일하기 → 검사 → 고치기를 정해진 조건이 될 때까지 반복하는 과정 전체 |
| **스펙(양식)** | 루프를 어떻게 돌릴지 적은 설정 파일(YAML). 이 문서가 정하는 "공통 양식" |
| **실행(run)** | 스펙 하나를 실제로 한 번 돌린 것. 같은 스펙을 여러 번 실행할 수 있음 |
| **반복(iteration)** | 실행 안의 한 바퀴. AI가 한 번 작업하고, 한 번 채점받는 단위 |
| **작업자(worker)** | 실제로 코드를 고치는 쪽. v1에서는 반복마다 새로 띄우는 Claude Code 세션 |
| **검증자(verifier)** | 결과를 채점·판정하는 장치. 예: 테스트 실행, 점수 계산 스크립트, 대전 평가 |
| **러너(runner)** | 루프 전체를 지휘하는 바깥 프로그램. 세션을 띄우고, 채점하고, 예산을 지키고, 멈출지 정함. 보고서의 "오케스트레이터" |
| **최선본(best)** | 지금까지 가장 점수가 좋았던 버전. 루프가 끝나면 마지막 버전이 아니라 이것을 돌려준다 |
| **봉인 평가(sealed)** | AI에게 결과를 절대 보여 주지 않는 평가. "AI가 평가에만 맞춰지고 있지 않나"를 몰래 확인하는 용도 |
| **사람 확인 지점(gate)** | 루프가 멈추고 사람의 승인을 기다리는 지점 |
| **보상 해킹** | 과제를 풀지 않고 채점을 속여 점수만 올리는 행동. 최신 모델에서도 흔함(보고서: METR 30.4%) |
| **worktree** | 같은 저장소의 작업 폴더를 하나 더 만드는 git 기능. 루프는 자기 전용 worktree에서 돌아 원래 작업을 건드리지 않는다 |

## 2. 목표와 범위

### 2.1 v1의 목표

1. 분야에 상관없이 쓸 수 있는 **루프 스펙 양식 v1**을 정한다.
2. 그 스펙을 읽어 루프를 돌리는 **러너**를 만든다(Claude Code를 반복마다 실행).
3. Argus에서 **루프 실행을 관찰하고**(점수, 반복, 비용, 경고), **사람 확인 요청에 답하고**, **멈출 수 있게** 한다.
4. 새로 참여할 Kaggle 대회를 첫 실제 사례로 돌려, 양식이 실제로 쓸 만한지 검증한다.

### 2.2 v1에서 하지 않는 것 (나중 버전)

| 하지 않는 것 | 이유 | 언제 |
|---|---|---|
| 여러 가지(branch)를 동시에 탐색하는 트리·진화 탐색 | 보고서: 탐색 방식보다 "작업 방식(연산자)과 실행 인프라"가 효과가 컸음(AIRA). 순차 개선으로 먼저 검증 | v2 |
| Argus 화면에서 스펙을 입력 양식으로 작성 | v1은 YAML 파일 + Argus의 검사·미리보기로 시작 (2026-10-29 결정) | v1.5 |
| Argus 화면의 버튼으로 루프 시작 | 웹 화면에서 AI 실행 프로세스를 띄우는 것은 보안 위험. v1은 터미널 명령으로 시작 | 검토 후 |
| Kaggle 자동 제출 | 하루 제출 한도가 있는 외부 행동. v1은 사람이 제출 | 검토 후 |
| LLM 판정자를 "정답 판정"에 쓰기 | 보고서: 같은 계열 모델의 자기 평가는 점수만 부풀림(Pan 2024). v1에서 LLM 판정자는 **감사용(점수에 미반영)**만 | v2 |
| AI의 생각 과정(CoT) 감시 | 연구 단계 기술. 감시 결과를 보상에 넣으면 오히려 숨기는 법을 배움(Baker 2025) | 나중 |
| RL 학습처럼 몇 시간짜리 원격 GPU 작업을 반복마다 돌리기 | 반복 한 번이 너무 길고 외부 장비가 필요 | v2 (`/loop` 감시와 결합) |

## 3. 설계 원칙 (선행연구에서 가져온 7가지)

| # | 원칙 | 쉬운 설명 | 근거 (보고서) |
|---|---|---|---|
| P1 | **검증자부터 설계한다** | 무엇으로 채점할지가 정해지지 않으면 루프를 만들지 않는다. 스펙에서 검증자가 필수 항목 | 결론, Reflexion(검증자 거짓 양성률이 품질 상한) |
| P2 | **바깥 신호로 채점한다** | AI가 "잘 됐어요"라고 말한 것이 아니라 실제 실행 결과로 채점. 같은 모델의 자기 비평만으로는 채점하지 않음 | Huang(75.8%→38.1%), Kamoi, Anthropic "최종 상태를 채점" |
| P3 | **검사와 예산은 러너가 쥔다** | 채점 코드, 예산, 스펙 파일은 AI가 고칠 수 있는 곳 밖에 둔다. "속이지 마"라는 지시는 통제 수단이 아니다 | METR(경고문 효과 거의 없음), RewardHackingAgents(평가기 잠금) |
| P4 | **잡음을 넘을 때만 "좋아졌다"고 본다** | 점수 차이가 우연한 흔들림보다 클 때만 채택 | Ladder(Blum & Hardt), ML-Master Δ 임계값 |
| P5 | **마지막이 아니라 최선본을 돌려준다** | 반복할수록 늘 좋아지지는 않는다 | Self-Refine, DSPy BestOfN |
| P6 | **멈추는 조건을 여러 개 둔다** | 반복 상한은 필수. 정체·발산·무결성 위반·이상 급등에서도 멈춘다 | 6갈래 종료 조건, 7가지 정지 조건 |
| P7 | **사람은 "루프 위"에 선다** | 매 반복을 승인하지 않고, 정해진 몇 지점에서만 판단한다. 대신 Argus가 "검증자의 건강 상태"를 보여 준다 | AI-native 문헌, 사람 개입 7지점, 결론("검증자 건강 계기판") |

## 4. 16개 부품 검토: v1에 무엇을 넣는가

보고서의 공통 스키마 16개 부품을 하나씩 검토했다. **포함** = v1에 넣음, **간단히** = 핵심만 넣음, **나중** = v1에서 뺌.

| # | 부품 | v1 결정 | v1에서의 모습 | 이유 |
|---|---|---|---|---|
| 1 | 목표 (goal) | **포함** | `objective`(한 문장), `success`(선택: 도달하면 성공 종료할 점수), `constraints`(지켜야 할 규칙 목록) | 루프의 출발점. 개선형 루프는 "성공" 없이 예산까지 최적화하는 것도 허용 |
| 2 | 작업 공간 (artifact) | **포함** | 러너가 전용 worktree와 브랜치를 만든다. `editable`(고쳐도 되는 경로), `protected`(절대 고치면 안 되는 경로). 반복마다 git 커밋 = 되돌리기 지점 | 되돌리기가 없으면 실패한 시도를 치울 수 없음(LATS). worktree는 이미 쓰는 방식 |
| 3 | 작업자 (worker) | **포함** | 반복마다 새 `claude -p` 세션. 모델, 지침, 권한, 반복당 제한 시간. 연산자는 `improve`(가설 하나·변경 하나)와 `debug`(실패 고치기) 두 개 | AIDE의 "한 번에 하나" 원칙. 새 세션이라 맥락이 깨끗함 |
| 4 | 검증자 (verifiers) | **포함** | 종류는 `command`(명령 실행 → JSON 결과) 하나로 시작. 각 검증자에 `trust`(믿음 등급)와 `access`(결과를 누구에게 보여 주나) 표시 | 테스트·점수 스크립트·대전 평가가 전부 "명령 실행"으로 표현됨. 가장 믿을 만한 종류부터 |
| 5 | 판정자 보정 (calibration) | **간단히** | 시작 전 "평가기 점검": 기준 버전을 두 번 채점(잡음 확인) + 일부러 나쁜 버전 채점(나쁘게 나오는지 확인). 결과를 사람이 보고 승인 | 보고서: 점수를 믿기 전에 평가기를 검증하라(Anthropic, CORE-Bench 42%→95%). LLM 판정자 보정은 v2 |
| 6 | 판정 기준 (acceptance) | **포함** | `metric`, `direction`(높을수록/낮을수록), 규칙은 `beats_best_by_margin` 하나. 여유폭 = max(상대 최소 개선, k × 표준오차). 사례별 점수가 있으면 **같은 시드끼리 짝지어 비교** | P4. 짝 비교는 잡음을 크게 줄임 |
| 7 | 피드백 규칙 (feedback) | **포함** | 작업자에게: 점수 변화, 채택 여부, 검증자 메시지(짧게). **무결성 위반은 일반 메시지만**("무결성 검사 실패") | 구체적 피드백이 효과적(Self-Refine). 단, 위반 이유를 자세히 알려 주면 회피를 배움(40.5% vs 20.3%) |
| 8 | 탐색 전략 (strategy) | **간단히** | `sequential` 하나: 항상 최선본에서 출발해 한 가지 개선 시도. 실패하면 되돌림 | 탐색 방식의 차이는 작았음(AIRA). 트리·병렬은 v2 |
| 9 | 상태·기억 (memory) | **포함** | 러너가 쓰는 추가 전용 기록(journal). 작업자 프롬프트에는 **최근 N개 시도 요약 + 최선본 정보 + 교훈 최대 3개**만 넣음 | 전체 이력이 아니라 범위를 정한 요약(AIRA, Reflexion 1~3개) |
| 10 | 예산 (budget) | **포함** | `max_iterations`(필수), `wall_clock`(전체 시간), 반복당 시간 제한, `usd`(선택). 모두 러너가 강제 | 기본 상한이 없는 프레임워크들의 교훈 → 반복 상한 필수 |
| 11 | 종료 조건 (stop) | **포함** | 성공, 반복 상한, 시간·비용 소진, 정체(N회 연속 채택 실패), 디버그 연속 실패, 발산, 이상 급등, 무결성 위반, 작업자의 "막힘" 신고, 사용자 중지 | 6갈래 + 7가지 정지 조건. 진동(같은 변경 반복) 감지만 v2로 미룸 |
| 12 | 종료 상태·반환 (on_exit) | **포함** | 종료 이유를 정해진 이름(열거값)으로 기록. 최선본 브랜치 + 상위 3개 목록 반환 | 종료 이유가 정해져 있어야 화면과 통계가 일관됨(Agent SDK subtype) |
| 13 | 무결성 가드 (guards) | **포함** | ① 검증자·스펙은 worktree 밖 ② 보호 경로 변경 검사 ③ 검증자 파일 해시 검사 ④ 세션 기록에서 금지 경로 접근 검사 ⑤ "막힘" 신고 통로 | 보상 해킹은 기본값(보고서). 구조적 차단만 믿는다 |
| 14 | 사람 확인 지점 (gates) | **간단히** | v1은 4곳: 시작 전 평가기 점검 승인, 이상·무결성 경보, 예산 연장, 최종 결과 검토 | 7지점 중 루프 안에서 실제로 필요한 것. Kaggle 제출은 v1에서 사람이 직접 하므로 게이트 불필요 |
| 15 | 기준선 (baselines) | **간단히** | 반복 0 = 시작 버전의 점수. 최종 보고에 "루프로 얼마나 나아졌나" 표시 | 루프의 가치를 숫자로 보여 줌. "같은 비용의 best-of-N" 비교는 v2 |
| 16 | 실행 방식·관측 (runtime, telemetry) | **포함** | 실행 방식은 `headless`(반복마다 `claude -p`) 하나. 반복마다 점수·비용·시간·판정·사유를 Argus에 보고 | Argus의 본업. OTel에는 루프 규약이 없어 Argus가 어휘를 정의 |

## 5. 루프 스펙 v1 (공통 양식)

### 5.1 파일 위치

스펙과 검증자는 **작업 대상 저장소 밖**, Argus의 데이터 폴더에 둔다. 작업자가 예산이나 채점 코드를 고칠 수 없게 하기 위해서다(P3).

```
~/.agents-observe/loops/<루프 이름>/
  spec.yaml              ← 스펙
  verifiers/             ← 채점 스크립트, 평가용 데이터(봉인 시드 등)
  runs/<실행 ID>/
    journal.jsonl        ← 반복 기록 (러너만 씀, 추가만 가능)
    logs/                ← 각 반복의 작업자 출력, 검증자 출력
```

작업 폴더(worktree)는 **대상 저장소 안의 `.worktrees/loop-<이름>-<실행ID>`**에 만든다. 대상 저장소의 `.gitignore`를 건드리지 않도록 러너가 `.git/info/exclude`에 `.worktrees/`를 추가한다. 루프 폴더와 작업 폴더를 분리하는 이유는, 작업 폴더에서 `../..`로 올라가도 검증자 폴더가 나오지 않게 하려는 것이다.

### 5.2 전체 구조 (예시로 보기)

```yaml
version: 1
name: example-loop
description: "무엇을 위한 루프인지 한두 문장"

goal:
  objective: "한 문장 목표"
  success:                       # 선택. 없으면 예산까지 계속 개선
    metric: main.score
    op: ">="
    value: 0.95
  constraints:                   # 작업자 프롬프트에 그대로 들어가는 규칙
    - "외부 네트워크를 쓰지 않는다"

workspace:
  repo: C:/Users/Jun/some-repo
  base_ref: main                 # 이 커밋에서 출발
  editable: ["src/**"]           # 고쳐도 되는 경로 (이 밖을 고치면 그 반복은 거절)
  protected: ["tests/**", "data/**"]   # 바뀌면 무결성 위반

worker:
  model: opus
  instructions: |                # 분야 설명, 코드 구조, 주의점
    ...
  operators: [improve, debug]
  permission_mode: bypassPermissions   # 모든 권한 (2026-10-29 결정)
  disallowed_tools:              # 모든 권한이어도 이것만은 막음 (되돌릴 수 없는 외부 행동)
    - "Bash(git push*)"
    - "Bash(kaggle competitions submit*)"
  timeout: 45m                   # 반복당 작업 시간 상한 (넘으면 러너가 종료)

verifiers:
  - id: gate
    kind: command
    run: "python {loop_home}/verifiers/smoke.py --candidate {worktree}"
    timeout: 5m
    trust: high
    access: dev                  # 결과를 작업자에게 보여 줌
    role: gate                   # 통과 못 하면 그 반복은 "실패(버그)"
  - id: main
    kind: command
    run: "python {loop_home}/verifiers/eval.py --set dev --candidate {worktree}"
    timeout: 20m
    trust: high
    access: dev
    role: score                  # 채택 판정에 쓰는 점수
  - id: sealed
    kind: command
    run: "python {loop_home}/verifiers/eval.py --set sealed --candidate {worktree}"
    timeout: 20m
    trust: high
    access: sealed               # 작업자에게 절대 안 보여 줌
    role: watch                  # 발산 감시와 최종 확인에만
    when: on_accept              # 채택된 반복에서만 실행

acceptance:
  metric: main.score
  direction: maximize
  rule: beats_best_by_margin
  margin:
    relative: 0.005              # 최소 0.5% 개선
    se_multiplier: 2             # 그리고 표준오차의 2배 이상 개선
  paired: true                   # 사례별 점수가 있으면 같은 사례끼리 비교

memory:
  show_last: 5                   # 프롬프트에 보여 줄 최근 시도 수
  reflections: 3                 # 교훈 최대 개수

calibration:                     # 시작 전 평가기 점검
  repeats: 2                     # 시작 버전을 몇 번 채점해 잡음을 볼지
  known_bad: "baseline/bad"      # 일부러 나쁜 버전(git 참조나 경로). 낮은 점수가 나와야 정상

budget:
  max_iterations: 20             # 필수 (debug 반복도 1회로 셈)
  wall_clock: 8h
  usd: 30                        # 선택

stop:
  plateau: { window: 4 }         # improve가 4번 연속 채택 실패 → 종료
  debug_chain: { max: 3 }        # 같은 실패를 3번 연속 못 고침 → 되돌리고 포기
  divergence: { window: 2 }      # main은 2번 채택됐는데 sealed는 안 좋아짐 → 일시정지
  anomaly: { se_multiplier: 8 }  # 표준오차 8배 넘는 급등 → 채택 전 일시정지

human_gates:
  start: required                # 평가기 점검 결과를 보고 승인해야 시작
  on_alert: pause                # 무결성·이상·발산 → 일시정지 후 사람 판단
  on_budget_end: ask             # 예산 소진 시 연장 여부를 물음 (stop이면 바로 종료)
  finish: review                 # 종료 후 결과 검토 표시

on_exit:
  return: best
  keep_top: 3
```

### 5.3 필드 정의

**표기:** 필수 = 반드시 적어야 함 / 기본값 = 안 적으면 이 값.

#### goal (목표)
| 필드 | 필수 | 설명 |
|---|---|---|
| `objective` | 필수 | 한 문장 목표. 작업자 프롬프트 맨 위에 들어감 |
| `success` | 선택 | `{metric, op, value}`. 최선본이 이 조건을 만족하면 `success`로 종료. 없으면 개선형 루프(예산까지 최적화) |
| `constraints` | 선택 | 작업자가 지켜야 할 규칙. **규칙을 써 두는 것은 안내일 뿐 통제 수단이 아니다**(P3). 지켜야 하는 것은 검증자나 가드로 확인해야 한다 |

#### workspace (작업 공간)
| 필드 | 필수 | 설명 |
|---|---|---|
| `repo` | 필수 | 대상 저장소 경로 |
| `base_ref` | 기본값 `HEAD` | 출발 커밋 |
| `editable` | 필수 | 고쳐도 되는 경로 패턴. 반복이 끝난 뒤 바뀐 파일이 이 밖에 있으면 그 반복은 거절 |
| `protected` | 선택 | 바뀌면 **무결성 위반**으로 처리하는 경로. `editable`과 겹치면 스펙 검사에서 오류 |

#### worker (작업자)
| 필드 | 필수 | 설명 |
|---|---|---|
| `model` | 기본값 사용자 설정 | `claude -p --model`로 전달 |
| `instructions` | 필수 | 분야 설명, 코드 구조, 해 볼 만한 방향 등 |
| `operators` | 기본값 `[improve, debug]` | v1은 이 두 개 (`draft`는 v2) |
| `permission_mode` | 기본값 `bypassPermissions` | `claude -p --permission-mode`. 사용자 결정(2026-10-29)으로 모든 권한이 기본값. 더 안전하게 하려면 `acceptEdits` + `allowed_tools` |
| `allowed_tools` | 선택 | `--allowedTools`. `acceptEdits`일 때 허용할 명령 목록 |
| `disallowed_tools` | 기본값 `git push`, Kaggle 제출 명령 | `--disallowedTools`. 모든 권한 모드에서도 이것만은 막는다(G10). 모든 권한 모드에서 이 차단이 실제로 작동하는지는 M1에서 확인(§16) |
| `timeout` | 기본값 `45m` | 반복당 작업 시간 상한. 넘으면 러너가 프로세스를 종료하고 그 반복은 `timeout` 실패 |

> **확인된 사실:** 설치된 Claude Code(2.1.312)의 `claude -p`에는 `--model`, `--permission-mode`, `--allowedTools`, `--disallowedTools`, `--settings`, `--session-id`, `--json-schema`, `--max-budget-usd`, `--append-system-prompt`가 있다. **반복당 턴 수 상한(`--max-turns`)은 없다.** 그래서 턴 수 대신 시간 상한(`timeout`)으로 통제한다.

#### verifiers (검증자) — 가장 중요한 부품
| 필드 | 필수 | 설명 |
|---|---|---|
| `id` | 필수 | 이름. 지표는 `<id>.<지표명>`으로 부름 (예: `main.score`) |
| `kind` | 필수 | v1은 `command`만 |
| `run` | 필수 | 실행할 명령. `{worktree}`, `{loop_home}`, `{run_dir}`, `{iteration}` 치환 가능 |
| `timeout` | 기본값 `20m` | 넘으면 검증자 실패 |
| `trust` | 필수 | `high`(테스트·지표 코드·시뮬레이터) / `medium`(LLM 판정 등) / `low`(같은 모델의 자기 평가) |
| `access` | 필수 | `dev`(결과를 작업자에게 보여 줌) / `sealed`(절대 안 보여 줌, 사람과 러너만) |
| `role` | 필수 | `gate`(통과 필수, 실패하면 버그로 처리) / `score`(채택 판정 점수) / `watch`(감시용, 판정에 직접 쓰지 않음) |
| `when` | 기본값 `every` | `every`(매 반복) / `on_accept`(채택 후보일 때만) / `final`(종료 시에만) |

**검증자 출력 약속(JSON, 표준 출력 마지막 줄):**
```json
{
  "ok": true,
  "metrics": { "score": 0.873 },
  "se": { "score": 0.012 },
  "cases": [ { "id": "seed-17", "score": 0.91 }, { "id": "seed-18", "score": 0.80 } ],
  "message": "작업자에게 보여 줄 짧은 설명 (dev 검증자만 전달됨)"
}
```
- `ok: false`면 실행 자체가 실패(예: 후보 코드가 크래시)한 것 → `gate`처럼 버그로 처리.
- `se`(표준오차)가 없으면 러너는 `relative` 기준만 쓴다.
- `cases`(사례별 점수)가 있으면 러너가 **최선본의 같은 사례 점수와 짝지어** 개선폭과 표준오차를 직접 계산한다. 시드를 고정한 시뮬레이션·테스트 묶음에서 잡음을 크게 줄인다.

**스펙 검사 규칙(러너가 시작 전에 확인):**
1. `role: score` 검증자가 정확히 하나 있어야 한다(P1).
2. `max_iterations`가 없으면 오류(P6).
3. `score` 검증자가 `trust: low`뿐이면 **경고 + `max_iterations`를 3으로 제한**(보고서: 약한 검증자면 3라운드 이하).
4. `sealed` 검증자가 없으면 경고("발산 감시 불가").
5. 검증자 명령이 작업 폴더 안의 파일을 실행하면 경고(작업자가 바꿀 수 있는 채점기).
6. `editable`과 `protected`가 겹치면 오류.

#### acceptance (판정 기준)
| 필드 | 설명 |
|---|---|
| `metric`, `direction` | 채택에 쓰는 지표와 방향(`maximize`/`minimize`) |
| `rule` | v1은 `beats_best_by_margin`만 |
| `margin.relative` | 최소 상대 개선폭 |
| `margin.se_multiplier` | 개선폭이 표준오차의 몇 배를 넘어야 하는지 |
| `paired` | `cases`가 있을 때 짝 비교 사용 |

**판정 식:** 후보 점수 − 최선본 점수(짝 비교면 사례별 차이의 평균) = d, 그 표준오차 = s 일 때
`d > max(relative × |최선본 점수|, se_multiplier × s)` 이면 **채택**. 그리고 모든 `gate` 검증자가 통과해야 한다.

#### calibration (평가기 점검)
| 필드 | 설명 |
|---|---|
| `repeats` | 기본값 2. 시작 버전을 이만큼 채점한다. 같은 입력인데 점수가 다르면 그 차이가 "잡음"이고, 사람 승인 화면에 표시된다 |
| `known_bad` | 선택. 일부러 나쁜 버전. 이것이 시작 버전보다 확실히 낮게 나오지 않으면 **평가기가 고장 났을 가능성**이 높으므로 시작 승인 화면에 경고한다(보고서: "여러 시도에서 0%면 대개 과제가 고장 난 것") |

#### budget / stop / human_gates / on_exit
위 5.2 예시의 주석 참고.

**종료·경보 조건의 정확한 판정 규칙:**

| 조건 | 판정 규칙 | 결과 |
|---|---|---|
| `plateau{window}` | **improve** 반복이 연속 `window`번 채택되지 않음 (debug 반복은 세지 않음, 채택되면 0으로 초기화) | 종료 `plateau` |
| `debug_chain{max}` | 같은 후보를 고치는 debug가 연속 `max`번 실패 | 최선본으로 되돌리고 그 후보 포기. 루프는 계속 (improve로 복귀) |
| `divergence{window}` | 마지막 봉인 점수가 **최근 `window`번 채택되기 전의 봉인 점수**보다 (봉인 표준오차 이상) 오르지 않았는데, 그 사이 dev 최선 점수는 `window`번 올랐음 | 일시정지 → 사람 확인 ② |
| `anomaly{se_multiplier}` | 채택 후보의 개선폭 d가 `se_multiplier × s`를 넘음 (너무 좋은 결과) | **채택 전에** 일시정지 → 사람 확인 ② |
| 무결성 위반 | §7의 G2(보호 경로)·G3(검증자 해시) 위반 | 해당 반복 거절. 첫 번째는 일시정지 → 사람 확인 ②, 두 번째는 종료 `integrity_violation` |
| 범위 밖 수정 | `editable` 밖 파일 변경 (보호 경로가 아닌 경우) | 해당 반복 거절, 작업자에게 **규칙만 다시 알려 줌**("고쳐도 되는 곳은 `agent/**`뿐"). 위반 감지 방법은 알려 주지 않음 |
| `needs_human` | 작업자 보고서에 `needs_human: true` | 일시정지 → 사람 확인 ② |

종료 이유는 아래 열거값 중 하나로 기록한다.

| 종료 이유 | 뜻 |
|---|---|
| `success` | 목표 점수 도달 |
| `max_iterations` | 반복 상한 도달 |
| `budget_time` / `budget_usd` | 시간·비용 소진 |
| `plateau` | 정체: improve가 연속으로 채택 실패 |
| `integrity_violation` | 무결성 위반 (사람이 중지 결정) |
| `escalated` | 작업자가 "막힘" 신고 후 사람이 중지 결정 |
| `user_stopped` | 사용자가 중지 |
| `error` | 러너 자체 오류, 사용량 한도 등 |

### 5.4 클래스와 프리셋 (2026-10-29 결정)

대회가 바뀌어도 스펙의 대부분은 똑같다. 그래서 스펙을 세 층으로 나눈다.

| 층 | 무엇 | 어디에 |
|---|---|---|
| **클래스** | 모든 대회가 공유하는 고정 구조와 기본값. v1은 `ml-improve`("ML 자동 개선") 하나 | Argus 저장소 `app/loop-runner/src/classes/` (Argus 코드와 함께 관리) |
| **프리셋** | 대회 유형별 기본값: `optimization` / `data` / `simulation` | 클래스 안 |
| **대회별 스펙** | 대회마다 다른 것만 적은 짧은 파일 | `~/.agents-observe/loops/<이름>/spec.yaml` |

러너는 짧은 스펙을 클래스·프리셋 규칙으로 **펼쳐서**(§5.2의 전체 형태로) 실행한다. 펼친 결과는 실행 기록에 함께 저장하고, Argus 미리보기 화면에도 보여 준다. **클래스를 고치면 그 클래스를 쓰는 모든 대회가 함께 좋아진다.**

#### `ml-improve` 클래스가 고정하는 것
- **검사 3단:** `quick`(빠른 검사, 통과 필수) → `score`(본 채점) → `sealed`(봉인 재확인, 채택 후보일 때만, 결과는 작업자에게 비공개)
- **채택:** `beats_best_by_margin`. 최선본을 돌려주고 상위 3개 보관
- **작업자:** 연산자 `improve`·`debug`, 모든 권한 + `git push`·Kaggle 제출 차단, 반복당 30분 (스펙에서 변경 가능)
- **기억:** 최근 시도 5개, 교훈 3개
- **종료:** 디버그 연속 3회 실패 시 되돌림, 정체 감지, 무결성 위반 정지 (§5.3 판정 규칙)
- **사람 확인 4곳:** 시작 승인, 경보, 예산 연장, 결과 검토
- **평가기 점검:** 시작 버전 2회 채점 + `known_bad`
- **기록 형식과 대시보드 화면 구성** (§9, §10)

#### 프리셋이 바꾸는 것

| | `optimization` | `data` | `simulation` |
|---|---|---|---|
| 예시 | 양자 회로 비용 최소화 (지금 대회) | 표·이미지 예측 | 봇 대전 |
| 점수 잡음 | 없음 (같은 입력이면 같은 값) | 폴드마다 흔들림 | 시드마다 흔들림 |
| 채택 여유폭 | 상대 0.1% | 상대 0.5% + 표준오차 2배 | 상대 1% + 표준오차 2배 |
| 짝 비교 | 안 함 | 폴드별 | 시드별 |
| `sealed`의 역할 | **gate** (다른 무작위 결과로도 반드시 통과) | **watch** (봉인 데이터로 발산 감시) | **watch** (봉인 시드·상대로 발산 감시) |
| 발산·이상 급등 감시 | 안 함 (점수가 결정적) | 함 | 함 |
| 평가기 점검의 "2회 채점" | 같은 값이어야 정상 (다르면 경고) | 잡음 크기 측정 | 잡음 크기 측정 |

#### 대회별 스펙 (짧은 형태)

```yaml
version: 1
class: ml-improve
preset: optimization
name: qc-invsqrt
description: "..."
goal:      { objective: "...", constraints: [...] }
workspace: { repo: ..., editable: [...], protected: [...] }
worker:    { instructions: "..." }            # 그 밖은 클래스 기본값
checks:
  quick:  { run: "...", timeout: 20m }
  score:  { run: "...", metric: cost, direction: minimize, timeout: 45m }
  sealed: { run: "...", timeout: 45m }
known_bad: "..."
budget:    { max_iterations: 5, wall_clock: 4h }  # 필수
overrides: {}                                  # 선택: 클래스·프리셋 기본값 덮어쓰기
```

**펼침 규칙:** `checks.quick` → `{trust: high, access: dev, role: gate, when: every}`, `checks.score` → `{trust: high, access: dev, role: score}`이고 `acceptance.metric = score.<metric>`, `checks.sealed` → `{trust: high, access: sealed, role: 프리셋에 따름, when: on_accept}`. **검사 규칙:** `checks.score`와 `budget.max_iterations`는 필수, `quick`·`sealed`가 없으면 경고.

## 6. 실행 구조

### 6.0 실행 방식을 고른 이유

Claude Code에서 루프를 돌리는 방법은 여러 가지다(보고서 "Claude Code의 루프 장치"). v1은 **"러너가 반복마다 `claude -p`를 새로 띄우는 방식"**을 고른다.

| 방식 | 장점 | v1에서 안 쓰는 이유 |
|---|---|---|
| **러너 + 반복마다 `claude -p`** (선택) | 채점·예산·멈춤 판단이 전부 작업자 밖. 반복마다 맥락이 깨끗함. 사람 확인 지점을 자유롭게 둘 수 있음. 러너가 꺼져도 기록으로 재개 | — |
| 한 세션 + Stop hook 채점 | 간단함 | 한 세션이 계속 길어져 맥락이 쌓임. 도구 호출 없이 8번 연속 막으면 hook이 무시됨. 채점이 작업자 세션 안에서 일어남 |
| `/goal` | 매우 간단함 | 판정 모델이 도구를 쓰지 않고 대화 기록만 읽음 → 작업자의 "통과했어요"에 속을 수 있음(보고서). 정답 판정에 부적합 |
| 동적 workflow | 병렬 가지, 결과 형식 검증 | 연구 미리보기 기능. 실행 중 사람 입력 불가, 스크립트 안에서 시간 측정 불가 → 사람 확인·시간 예산을 바깥에서 따로 처리해야 함. v2의 병렬 탐색에서 다시 검토 |

### 6.1 구성 요소

```
┌──────────────┐   스펙 읽기    ┌────────────────────────────┐
│ spec.yaml     │──────────────▶│ 러너 (argus-loop)           │
│ verifiers/    │◀──채점 실행────│  - 세션 띄우기 / 시간 제한   │
└──────────────┘               │  - 무결성 검사 / 채점 / 판정 │
                               │  - 기록(journal) / 멈춤 판단 │
                               └───┬──────────────────┬──────┘
                    claude -p 실행 │                  │ 진행 보고 (HTTP)
                                   ▼                  ▼
                   ┌──────────────────────┐   ┌──────────────────────┐
                   │ Claude Code 세션      │   │ Argus 서버 + 화면      │
                   │ (작업자, worktree 안) │──▶│ 루프 목록·상세·경고    │
                   └──────────────────────┘   │ 사람 확인 응답, 중지   │
                     hook 이벤트(기존 경로)   └──────────────────────┘
```

- **러너**는 Argus 저장소 안의 새 Node 프로그램(`app/loop-runner/`)이다. 터미널에서 `argus-loop run <루프 이름>`으로 시작한다.
- **작업자 세션**은 기존 hook을 그대로 통해 Argus에 기록된다. 러너가 `--session-id`로 세션 ID를 미리 정해 주므로, "반복 7번 = 세션 X"가 정확히 연결된다. 덕분에 Argus의 기존 세션 화면과 비교 화면을 그대로 쓸 수 있다.
- **Argus 서버가 꺼져 있어도 루프는 돈다.** 진실의 원본은 러너가 쓰는 `journal.jsonl`이고, Argus는 그것을 보여 주는 거울이다. 이 경우 사람 확인 요청은 러너의 터미널에서 묻는다.
- **작업자 세션이 물려받는 설정:** `claude -p`는 기본적으로 사용자 설정(`~/.claude/settings.json`)의 hook과 권한을 그대로 쓴다. 그러면 Argus 기록 hook뿐 아니라 **루프와 상관없는 다른 hook**(예: 프롬프트마다 "작업 목록을 만들라"는 안내를 붙이는 hook)도 작업자에게 영향을 준다. M1에서 `--setting-sources`와 `--settings`로 **Argus 기록 hook + 루프용 권한만** 주는 구성을 만들고, 그래도 Argus에 기록되는지 확인한다(§16).

### 6.2 한 번의 실행 흐름

```
[준비]
 1. 스펙 검사 (§5.3 규칙) → 오류면 중단
 2. worktree + 브랜치 생성 (base_ref에서)
 3. 검증자 파일 해시 저장
 4. 평가기 점검: 시작 버전을 2번 채점(잡음 확인), known_bad가 있으면 채점(나쁘게 나오는지)
 5. 반복 0 = 시작 버전 점수 = 첫 최선본, 기준선으로 기록
 6. [사람 확인] 평가기 점검 결과 승인 → 시작

[반복 n]
 7. 연산자 결정: 직전이 버그면 debug(실패한 버전에서 계속), 아니면 improve(최선본에서 출발)
 8. 프롬프트 구성 (§6.3) → claude -p 실행 (시간 제한)
 9. 작업자 종료 → 결과 보고(JSON) 읽기, 비용·턴 수 기록
10. 무결성 검사 (§7): 범위 밖 수정 → 거절 / 보호 경로·검증자 변경 → 위반
11. 변경 사항 커밋 (러너가 직접)
12. 검증자 실행: gate → score → (채택 후보면) sealed
13. 판정: 채택이면 최선본 갱신, 아니면 최선본으로 되돌림 (debug 대상이면 유지)
14. 경보 확인: 이상 급등 / 발산 / 무결성 → [사람 확인]으로 일시정지
15. 기록(journal) 추가, Argus에 보고
16. 종료 조건 확인 → 계속이면 7로

[마무리]
17. 상위 3개 후보를 sealed 검증자로 최종 채점 (when: final 검증자 포함)
18. 최선본 브랜치 확정, 요약 보고서 작성 (기준선 대비 개선폭, 종료 이유, 비용)
19. [사람 확인] 최종 결과 검토
```

### 6.3 작업자에게 주는 프롬프트

러너가 반복마다 새로 조립한다. 순서는 이렇다.

1. **목표**와 **규칙**(`objective`, `constraints`)
2. **작업 범위:** "고쳐도 되는 곳: `editable` / 고치면 안 되는 곳: `protected`"
3. **분야 설명**(`instructions`)
4. **현재 최선본:** 점수, 어떤 변경들로 여기까지 왔는지 (가설 한 줄씩)
5. **최근 시도 N개:** 가설 → 결과(채택/거절/버그), 점수 변화, 검증자 메시지 (dev 검증자만)
6. **교훈** 최대 3개 (러너가 반복 기록에서 뽑거나, 작업자가 보고한 것 중 최근 것)
7. **이번 할 일:**
   - improve: "가설 하나를 정하고, 그것을 검증할 **한 가지 변경**만 하라."
   - debug: "직전 시도가 아래 오류로 실패했다. 원인을 찾아 고쳐라." + 오류 출력(앞뒤를 잘라 짧게)
8. **결과 보고 형식:** `--json-schema`로 강제

```json
{
  "hypothesis": "무엇을 시도했고 왜 좋아질 거라 봤는지",
  "change_summary": "무엇을 바꿨는지",
  "lesson": "다음 시도에 남길 교훈 (선택)",
  "needs_human": false,
  "needs_human_reason": ""
}
```

`needs_human: true`는 **정당한 탈출구**다. 목표가 불가능하거나 규칙끼리 충돌할 때 속이지 말고 사람을 부르라는 통로다(보고서: 이 통로를 주자 부정행위가 54%→9%로 줄었다). 러너는 이것을 받으면 일시정지하고 사람에게 묻는다.

### 6.4 상태 흐름 (Argus가 그릴 그림)

```
준비 → 점검 → [시작 승인 대기] → 작업 → 무결성 검사 → 채점 → 판정 ─┬─▶ 작업 (다음 반복)
                                     ▲                              ├─▶ [경보: 사람 판단 대기] ─▶ 작업 / 중지
                                     └──────── 재개 ◀── [일시정지] ◀─┤
                                                                    └─▶ 마무리 → [결과 검토] → 완료
```

### 6.5 실패 처리

| 상황 | 처리 |
|---|---|
| 작업자가 시간 초과 | 프로세스 종료(Windows는 자식 프로세스까지 종료), 그 반복은 `timeout` 실패, 최선본으로 되돌림 |
| 작업자 세션 오류 종료 | `error` 반복으로 기록, 한 번 재시도, 다시 실패하면 일시정지 |
| Claude 사용량 한도에 걸림 | 일시정지(`waiting_quota`), Argus에 표시. 시간은 예산에서 빼지 않음 |
| 검증자 시간 초과·크래시 | 후보 버그(`ok: false`)와 구분: 검증자 자체 오류면 일시정지하고 사람에게 알림 |
| 러너가 중간에 꺼짐 | 다시 실행하면 journal을 읽고 마지막 완료 반복 다음부터 재개 |
| 같은 루프를 동시에 두 번 실행 | 잠금 파일로 막음 |

## 7. 안전장치 (무결성)

보고서는 "보상 해킹은 예외가 아니라 기본값"이라고 정리한다. v1의 안전장치와, 각각이 막는 행동은 이렇다.

| # | 장치 | 막는 행동 | 한계 |
|---|---|---|---|
| G1 | 검증자·스펙·예산을 작업 폴더 밖(`~/.agents-observe/loops/`)에 둠 | 채점 코드 수정, 예산 늘리기 | 같은 PC라서 셸 명령으로 읽는 것까지는 못 막음 → G4로 감지 |
| G2 | 반복 후 바뀐 파일 검사: `editable` 밖 → 거절, `protected` → 위반 | 테스트·데이터·엔진 변조 | 없음 (git이 정확히 앎) |
| G3 | 검증자 파일 해시를 매 반복 확인 | 작업 폴더 밖까지 손대는 행동 | 바뀌면 즉시 정지 |
| G4 | 세션 기록에서 금지 경로(루프 폴더) 접근을 찾음 | 봉인 데이터 엿보기, 채점기 분석 | 문자열 검사라 우회 가능. 경보용 |
| G5 | 채점은 러너가 직접 실행, 작업자가 출력한 숫자는 무시 | "점수 0.99 나왔어요" 같은 허위 보고 | 없음 |
| G6 | `sealed` 검증자 결과는 작업자에게 안 보여 줌 | 평가 세트에만 맞추기 | 봉인 데이터 자체를 엿보면 무력화 → G4 |
| G7 | 무결성 위반은 일반 메시지로만 알림, 두 번째 위반은 정지 | 감지 방식을 배워 피하기 | — |
| G8 | 권한: 기본은 **모든 권한**(사용자 결정). 대신 전용 worktree 안에서만 일하게 하고, `disallowed_tools`로 외부 행동만 막음 | 막힘 없이 일하게 하되, 되돌릴 수 없는 행동만 차단 | 모든 권한이므로 작업 폴더 밖 파일도 고칠 수 있다. 이것은 G2(바뀐 파일 검사)·G3(검증자 해시)로 **사후에 감지**한다. 위험이 크다고 판단되면 스펙에서 `acceptEdits`로 바꿀 수 있다 |
| G9 | `needs_human` 탈출구 | 막혔을 때 속이는 행동 | — |
| G10 | **러너는 push·merge·제출을 하지 않는다.** 작업자 허용 명령에도 `git push`, Kaggle 제출 명령을 넣지 않는다(스펙 검사에서 경고) | 되돌릴 수 없는 외부 행동 (보고서: Replit 사고) | 최선본은 로컬 브랜치로만 남고, 합치기와 제출은 사람이 한다 |

**정직하게 말해 둘 점:** 같은 PC에서 도는 이상 작업자가 마음먹으면 루프 폴더의 파일을 **읽는 것**까지 완전히 막을 수는 없다. 그래서 v1은 "**바꾸는 것은 막고, 읽는 것은 감지한다**"를 목표로 한다. 완전한 격리(별도 사용자 계정이나 컨테이너)는 필요해지면 v2에서 검토한다.

## 8. 사람 확인 지점 (v1: 4곳)

| 지점 | 언제 | 사람이 보는 것 | 선택지 |
|---|---|---|---|
| ① 시작 승인 | 평가기 점검 직후 | 시작 버전 점수 2회(잡음), 일부러 나쁜 버전 점수, 스펙 요약, 검사 경고 | 시작 / 취소 |

응답은 **Argus 화면의 버튼** 또는 **러너 터미널** 어느 쪽에서도 할 수 있다. 먼저 온 응답을 쓴다.

## 9. Argus 화면

### 9.1 루프 목록
- 사이드바 위쪽에 **"루프"** 탭을 추가한다(프로젝트·라벨 탭과 같은 줄).
- 목록 한 줄: 이름, 상태(작업 중 / 일시정지 / 사람 확인 대기 / 완료), 반복 진행(7/20), 최선 점수(기준선 대비 +%), 누적 비용, 시작 시각
- **사람 확인 대기 중인 실행은 맨 위에 강조**한다(기존 알림 벨과 같은 방식).

### 9.2 실행 상세
- **상태 줄:** 현재 단계, 종료 이유, 예산 게이지 3개(반복 / 시간 / 비용), [중지] 버튼
- **점수 그래프:** 가로축 = 반복, 점 = 각 반복의 점수(채택 ● / 거절 ○ / 버그 ×), 선 = 최선본 점수, 다른 색 점 = 봉인 점수.
  → **"검증자 건강 상태"**를 한눈에 본다. dev 선은 오르는데 봉인 점이 제자리면 과적합 신호(보고서 결론).
- **반복 표:** 번호, 연산자, 가설, 판정, 점수 변화(±표준오차), 비용, 시간, [세션 보기], [최선본과 비교]
  - [세션 보기] = 기존 세션 화면으로 이동
  - [최선본과 비교] = 이미 만든 **2세션 비교 화면**에 이 반복 세션과 최선본 세션을 띄움
- **확인 요청 카드:** §8의 내용과 선택 버튼
- **경보 목록:** 무결성, 이상, 발산, 검증자 오류

### 9.3 루프 세션을 사이드바에서 묶기
반복마다 세션이 하나씩 생기므로, 그대로 두면 사이드바가 루프 세션으로 가득 찬다(20회 실행이면 20개).
- 러너가 각 세션 이름을 `loop:<루프 이름> #<실행>-<반복>`으로 붙인다(기존 세션 이름 변경 API 사용).
- 사이드바의 프로젝트 목록에서는 루프 세션을 **기본으로 숨기고**, 루프 실행 상세의 반복 표에서 연다. 설정에서 "루프 세션도 보기"를 켤 수 있게 한다.

### 9.4 스펙 보기 (v1은 읽기 전용)
- 스펙을 §4의 부품 단위 카드로 보여 준다(목표 / 작업 범위 / 작업자 / 검증자 / 판정 / 예산 / 종료 / 사람 확인).
- 스펙 검사 경고를 같이 표시한다(예: "봉인 검증자가 없어 발산 감시를 할 수 없습니다").

## 10. 데이터 구조와 API (개발용)

## 11. 첫 적용: Kaggle 대회

**상태(2026-10-29):** Kaggriculture는 종료되었고, 첫 대회는 **[Google Quantum AI - Verifiable Quantum Circuit Compilation](https://www.kaggle.com/competitions/google-verifiable-quantum-circuit-compilation)**(마감 2027-01-20)로 정했다. 회로를 공식 검증기로 검사하고 비용(큐비트·게이트 수)으로 채점하는 **최적화형** 대회다(§5.4 `optimization` 프리셋). 세 문제 중 **invsqrt부터** 시작하고, dfthcsos가 다음이다. **dqi는 제외**한다: 기준 회로 검사만으로 이 PC의 WSL 메모리(7GB)를 넘어 강제 종료되었다. 아래는 데이터형·시뮬레이션형 대회에 쓸 참고 설계로 남긴다.

| 문제 | 전체 검사 1회 (기준 회로) | 메모리 | 상태 |
|---|---|---|---|
| invsqrt | 282초 | 0.5GB | 첫 루프 대상 |
| dfthcsos | 95초 | 1.1GB | 다음 |
| dqi | 392초 후 강제 종료 | 7.4GB 초과 | 제외 |

Kaggle 대회는 크게 두 유형이라 유형마다 검증자 구성이 다르다.

| 유형 | 순위를 정하는 것 | 루프의 채점(score 검증자) | 가장 큰 위험 | 정리된 곳 |
|---|---|---|---|---|
| **데이터형** (표·이미지·텍스트 예측) | 숨겨진 테스트 데이터에 대한 예측 점수 | 고정된 교차검증(CV) 점수를 **러너 쪽 스크립트가 다시 계산** | 데이터 누수, 검증 분할 과적합 | §11.0 |
| **시뮬레이션형** (봇끼리 대전) | 다른 참가자 봇과의 대전 결과 | 고정 상대·고정 시드 대전 점수 차이 | 엔진·상대 변조, 상대 묶음 과적합 | §11.1~11.6 (Kaggriculture 예시) |

### 11.0 데이터형 대회의 검증자 (보고서 "Kaggle 모델 개선에 적용하기" 요약)

| id | 무엇을 하나 | trust | access | role |
|---|---|---|---|---|
| `submission_check` | 학습·예측 스크립트가 에러 없이 끝나고 `submission.csv` 형식이 맞는지 | high | dev | gate |
| `cv` | 루프를 만들 때 **사람이 승인한 분할**(`folds.csv`, 루프 폴더에 보관)로, 작업자가 낸 OOF 예측(`oof.npy`)에서 **러너 쪽 `score.py`가 점수를 다시 계산**. 폴드별 점수를 `cases`로 내보내 짝 비교 | high | dev | score |
| `holdout` | 학습 데이터의 약 10%를 작업자가 읽을 수 없게 떼어 둔 봉인 세트로 채점 | high | sealed | watch |
| `leak_check` | 전처리 코드에 테스트 정보나 타깃이 새어 들어갔는지 (v1은 규칙 기반 스크립트, LLM 검사는 v2) | medium | dev | gate |
| `public_lb` | 공개 리더보드 점수. 사람이 제출하고 기록만 함 | medium | sealed | 기록 전용 |

- **분할 방식(StratifiedKFold, GroupKFold, 시계열 분할 등)은 사람이 정한다.** 루프 전체의 신뢰도를 정하는 결정이라 AI가 고를 일이 아니다(보고서 사람 게이트).
- **보호 경로:** 데이터 폴더, `folds.csv`, `score.py`, 봉인 세트는 작업 폴더 밖 루프 폴더에 둔다.
- **최종 제출은 사람이 고른다:** 최고 CV 하나와 성격이 다른 강건한 후보 하나처럼, 상위 후보 목록(`keep_top`)에서 고른다. 보고서는 최고 검증 점수 하나만 고르면 손해가 컸다고 보고한다(AIRA).

### 11.1 시뮬레이션형 예시: Kaggriculture 상황 정리 (종료된 대회, 저장소·메모 기준)
- 2인 대전 농장 시뮬레이션. 720턴(하루 24턴 × 30일), 10×10 농장, 함께 쓰는 시장.
- 공식 엔진과 **비트 단위로 똑같은 Rust 엔진**이 있고, 공식보다 약 2,200배 빠르다(단일 스레드 약 156만 스텝/초).
- RL 학습 코드(PPO 자가 대전)가 있고, 학습은 Kaggle 노트북·vast.ai GPU에서 돈다. 로컬 PC는 개발용.
- **알려진 함정:** 2번 자리(seat 1) 플레이어는 `obs["step"]`을 받지 못한다. 턴은 day×24+hour로 계산해야 한다.
- 대회는 종료되었다(2026-10-29 사용자 확인). 아래 11.2~11.6은 **새 대회가 시뮬레이션형일 때 그대로 옮겨 쓸 수 있는 예시**로 남긴다.

### 11.2 무엇을 개선하는 루프인가
일반 Kaggle 대회는 "검증 데이터 점수"로 채점하지만, 이 대회는 **대전 결과**로 순위가 정해진다. 그래서 검증자는 **"고정된 상대들과, 고정된 시드로, 양쪽 자리 모두에서 대전한 점수 차이"**다.

개선 대상 후보는 두 가지다. 새 대회가 시뮬레이션형이면 같은 기준으로 고른다.

| 후보 | 반복 1번의 비용 | v1 적합도 |
|---|---|---|
| **A. 규칙 기반 봇 또는 제출용 컨트롤러 로직** (작업자가 코드를 고치면 바로 대전 평가) | 수 분 예상 (로컬 CPU, 미측정 §11.6) | **높음 (추천)** |
| B. RL 정책 (학습 설정·보상·구조를 고치고 GPU에서 학습 후 평가) | 수 시간 (원격 GPU) | 낮음 → v2 |

### 11.3 검증자 설계

| id | 무엇을 하나 | trust | access | role |
|---|---|---|---|---|
| `smoke` | 공식 `kaggle_environments`에서 **실제 제출 진입점**으로 2~4판 실행. 크래시·시간 초과·`obs["step"]` 의존(2번 자리) 확인, 한 턴당 응답 시간 측정 | high | dev | gate |
| `dev_eval` | Rust 엔진으로 **dev 시드 묶음 × 양쪽 자리 × 상대 묶음** 대전. 지표 = 평균 점수 차이(내 돈 − 상대 돈), 보조 지표 = 승률. 시드별 점수를 `cases`로 내보내 **짝 비교** | high | dev | score |
| `sealed_eval` | **다른 시드 묶음 + 작업자가 모르는 상대 1개 이상**으로 같은 평가. 채택 후보일 때만 | high | sealed | watch |
| `public_lb` | Kaggle 리더보드 점수. 사람이 제출하고 기록만 함 | medium | sealed | 기록 전용 (판정·보상에 안 씀) |

**상대 묶음(고정, 루프 폴더에 보관):**
- 무작위 봇(저장소의 `RandomIntentBot` 계열), 아무것도 안 하는 봇(PASS)
- 시작 버전의 봇 사본(기준선)
- 가능하면 학습된 RL 체크포인트 하나 (봉인 상대로 쓰기 좋음)

**왜 "짝 비교"가 특히 중요한가:** 같은 시드면 날씨·시장 같은 무작위 요소가 똑같다. 그래서 후보와 최선본의 차이를 시드별로 빼면 운의 몫이 대부분 사라지고, 적은 판수로도 "진짜 좋아졌는지"를 판단할 수 있다.

**왜 "양쪽 자리"인가:** 1번 자리와 2번 자리의 관측이 다르다(위의 `obs["step"]` 함정). 한쪽 자리에서만 평가하면 다른 쪽 자리의 버그를 놓친다.

**일반 Kaggle 대회와 다른 점:** 일반 대회의 가장 큰 위험은 데이터 누수(테스트 정보가 학습에 섞임)라서 보고서는 누수 검사기를 필수로 꼽았다(MLE-STAR). 이 대회에는 나눌 데이터가 없어서 누수 검사는 필요 없다. 대신 같은 자리에 **"엔진과 상대를 건드리지 못하게 하는 것"**이 들어간다(아래 11.4).

### 11.4 Kaggriculture 전용 안전장치
- **엔진은 보호 경로다.** `engine/`, `parity/`, `third_party/`를 `protected`에 넣는다. 작업자가 엔진을 자기에게 유리하게 고치는 것은 가장 큰 위험이다.
- **평가는 루프 폴더의 고정 엔진으로 한다.** 루프를 만들 때 `dist/`의 `kagg` 휠을 루프 전용 가상환경에 설치해 두고, 검증자는 작업 폴더의 엔진 빌드가 아니라 **이 고정본**으로 대전한다. 작업 폴더의 엔진이 바뀌어도 채점에는 영향이 없다.
- **상대 봇과 시드 목록은 루프 폴더에만 있다.** 작업 폴더에는 없다.
- **리더보드는 보상이 아니다.** 반복 수백 번이 리더보드에 맞춰지면 실력이 아니라 리더보드에 과적합된다(보고서 Ladder). 제출은 사람이 하고, 점수는 dev·봉인 점수와 나란히 기록만 해서 상관을 본다.

### 11.5 Kaggriculture 스펙 예시 (출발값, 실측 후 조정)

```yaml
version: 1
name: kagg-bot
description: "Kaggriculture 봇의 대전 성능 개선"

goal:
  objective: "고정 상대 묶음과의 대전에서 평균 점수 차이(내 돈 − 상대 돈)를 최대화한다"
  constraints:
    - "제출 봇은 obs['step']을 쓰지 않고 day*24+hour로 턴을 계산한다"
    - "한 턴 응답 시간은 대회 제한 안에 있어야 한다"

workspace:
  repo: C:/Users/Jun/Kaggriculture-2026
  base_ref: main
  editable: ["agent/**"]            # 실제 봇 코드 위치에 맞춰 수정
  protected: ["engine/**", "parity/**", "third_party/**", "train/**"]

worker:
  model: opus
  instructions: |
    (게임 규칙 요약, 봇 코드 구조, 지금까지 알려진 전략과 함정)
  operators: [improve, debug]
  permission_mode: bypassPermissions
  disallowed_tools: ["Bash(git push*)", "Bash(kaggle competitions submit*)"]
  timeout: 40m

verifiers:
  - { id: smoke,       kind: command, trust: high, access: dev,    role: gate,
      run: "{loop_home}/venv/Scripts/python {loop_home}/verifiers/smoke.py --agent {worktree}/agent/main.py",
      timeout: 10m }
  - { id: dev_eval,    kind: command, trust: high, access: dev,    role: score,
      run: "{loop_home}/venv/Scripts/python {loop_home}/verifiers/eval.py --set dev --agent {worktree}/agent/main.py",
      timeout: 30m }
  - { id: sealed_eval, kind: command, trust: high, access: sealed, role: watch, when: on_accept,
      run: "{loop_home}/venv/Scripts/python {loop_home}/verifiers/eval.py --set sealed --agent {worktree}/agent/main.py",
      timeout: 30m }

acceptance:
  metric: dev_eval.margin
  direction: maximize
  rule: beats_best_by_margin
  margin: { relative: 0.01, se_multiplier: 2 }
  paired: true

calibration:
  repeats: 2
  known_bad: "{loop_home}/verifiers/opponents/random_bot.py"   # 무작위 봇이 확실히 낮게 나와야 정상

budget:
  max_iterations: 20
  wall_clock: 10h

stop:
  plateau: { window: 4 }
  debug_chain: { max: 3 }
  divergence: { window: 2 }
  anomaly: { se_multiplier: 8 }

human_gates: { start: required, on_alert: pause, on_budget_end: ask, finish: review }
on_exit: { return: best, keep_top: 3 }
```

### 11.6 시뮬레이션형 대회에서 미리 재야 할 것 (M4 첫 작업)
- 봇 한 판(720턴)에 걸리는 시간 → dev 평가 판수와 병렬 프로세스 수 결정. 엔진은 빠르지만 **봇의 파이썬 판단 시간이 대부분**일 것으로 예상(미측정).
- 같은 시드로 두 번 돌렸을 때 점수가 같은지(결정성). 같다면 잡음은 "시드 간 차이"뿐이라 짝 비교 효과가 크다.
- 대회의 한 턴 응답 시간 제한, 하루 제출 한도, 최종 순위 방식(대회 규칙 페이지).

## 12. 단계별 구현 계획

각 단계는 **따로 브랜치·커밋**하고, 끝날 때마다 결과를 보여 드린 뒤 다음으로 넘어간다.

| 단계 | 만드는 것 | 완료 기준 |
|---|---|---|
| **M1. 러너 핵심** | 스펙 읽기·검사, worktree 준비, `claude -p` 실행(시간 제한), 무결성 검사 G1~G3·G5, command 검증자, 판정 식, 종료 조건, journal, 재개 | ① 가짜 작업자(스크립트)로 모든 종료 이유가 재현되는 자동 테스트 통과 ② 작은 연습 루프(예: 느린 함수를 테스트를 지키며 빠르게)를 **실제 Claude로** 끝까지 한 번 실행 |
| **M2. Argus 연결** | 서버 테이블·API·WebSocket, 러너의 진행 보고, 루프 목록·실행 상세 화면(그래프, 반복 표, 세션 링크, 비교 화면 연결), 중지 버튼 | M1 연습 루프를 Argus에서 실시간으로 보고 중지할 수 있음 |
| **M3. 사람 확인과 경보** | 확인 지점 4곳(화면 버튼 + 터미널), 봉인 검증자, 발산·이상 감지, G4(세션 기록 검사), `needs_human` 처리 | 일부러 만든 "이상 급등"과 "보호 파일 수정" 시나리오에서 루프가 멈추고 화면에 확인 요청이 뜸 |
| **M4. 첫 대회 적용** | 대회 선택 → 유형에 맞는 루프 폴더 구성. 데이터형: 분할·`score.py`·봉인 세트(§11.0). 시뮬레이션형: 고정 엔진 가상환경·상대 묶음·dev/봉인 시드·`smoke.py`·`eval.py`(§11.3~11.6). 반복 1회 시간 실측 → 예산 결정(§15-2) | 평가기 점검 통과(잡음 확인, 일부러 나쁜 버전이 확실히 낮은 점수) → 실제 루프 1회 실행 → 결과 보고 |
| **M5. 다듬기 (v1.5~v2)** | 스펙 입력 양식, LLM 감사 판정자, 트리·병렬 탐색, 진동 감지, RL 장기 작업, **단계식 평가**(적은 판수로 먼저 거르고 유망한 후보만 전체 판수로 채점 — 보고서의 successive halving), 반복당 도구 호출 수 상한(PreToolUse hook으로 셈) | 별도 설계 |

## 13. 테스트 계획

- **판정·종료 로직은 순수 함수로** 만들어 단위 테스트한다(짝 비교 계산, 여유폭, 정체·발산·이상 판정, 종료 이유).
- **가짜 작업자:** 러너가 `claude -p` 대신 지정한 스크립트를 실행하는 시험 모드를 둔다. 정해진 점수 흐름을 흉내 내서 **토큰을 쓰지 않고** 모든 경로(채택, 거절, 버그, 시간 초과, 범위 밖 수정, 보호 파일 수정, 검증자 변조, 막힘 신고)를 확인한다.
- **재개 테스트:** 반복 중간에 러너를 강제로 끄고 다시 켜서 이어지는지.
- **실제 실행:** M1과 M4에서 각각 한 번씩 진짜 Claude로 끝까지 돌려 본다.
- 기존 Argus 테스트 전체가 계속 통과해야 한다.

| 같은 저장소에서 다른 세션과 충돌 | 루프는 자기 worktree만 사용 |
